# @imprentajs/pdf

The engine as a Node addon, plus the streaming wrapper. See the root
`CLAUDE.md` for the rules that apply everywhere.

## What is generated and what is written

```
index.js          generated by napi — do not edit
index.d.ts        generated by napi — do not edit
imprenta.*.node   the compiled crate
src/stream.ts     written by hand: the Printer, a thin wrapper over DocumentStream
```

`index.*` and the `.node` come from `crates/imprenta-pdf-napi`. Editing them by
hand produces a change that survives until the next build and no longer.

## What gets published

Six packages, not one: `@imprentajs/pdf` and an `@imprentajs/pdf-<platform>` for
each entry in `napi.targets`. The addons are compiled by `.github/workflows/
publish.yml`, one job per target, and the per-platform packages are generated
at publish time by `napi create-npm-dirs` — nothing under `npm/` is committed,
because every field in it is derived from this `package.json`.

**`files` must not list `*.node`.** `index.js` tries the local addon first and
falls back to the platform package, so a binary here would be picked up and
shipped inside the main package — 5 MB of one platform's addon inside the
package whose entire job is to choose between five. `napi artifacts` drops a
copy of every addon in this directory as a side effect of staging, so this is
not hypothetical; `publish.yml` packs a dry run and fails if one ever gets in.

## Build before you test

```bash
pnpm --filter @imprentajs/pdf build        # release — what tests and benchmarks use
pnpm --filter @imprentajs/pdf build:debug  # faster to compile, never benchmark on it
```

Any change under `crates/` needs this before a Node test means anything. A
stale binary makes tests pass by comparing two documents that are both missing
the field you just added.

## The API surface, and why it is that shape

- `render(ir, options)` → `{ pdf, pages, bytes, diagnostics }`
- `renderToFile(ir, path, options)` → no Buffer ever exists; use it for anything
  large
- `new Printer(page, options)` from `@imprentajs/pdf/stream` — feed a document in
  pieces

`ir` is a **JSON string**, not an object. That is not an oversight: it is
faster than walking an object across the boundary, and it is also what comes
back from a file, a queue or an HTTP body.

Images are handed over as bytes and a name, nothing else. Format and pixel size
are read from the file — a caller that has to declare them is a caller that can
squash a logo silently.

## Printer rules

- **Await every call before the next.** A second call while one is running is
  refused with a rejection. Queueing batches would put the document back in
  memory by the route the Printer exists to avoid.
- **Batch.** Sending rows or nodes one at a time costs a round trip each and is
  *slower* than not streaming — measured, 2.5 s against 1.33 s on a hundred
  thousand rows. A hundred to a thousand per batch. Ten thousand buys nothing
  and doubles the heap.
- **A document with no table streams too.** `printer.nodes(batch)` is the whole
  API for a transcript, a log or a book, and batching matters just as much
  there. Any benchmark added here must include a table-less case; every early
  one was table-shaped and hid a 26% regression.
- Bands are given to the constructor, not fed as pieces: the paginator has to
  know how much room a header takes before it packs the first row.

## Testing

`packages/pdf/test/` is for what genuinely needs Node running — promise
behaviour, rejection, ordering, the Buffer-versus-file paths. Engine behaviour
belongs in `cargo test`, where it runs in a fraction of the time.

The test that matters most: content fed in pieces is **byte for byte** what the
same content declared whole produces. Keep it, and keep it comparing bytes.
