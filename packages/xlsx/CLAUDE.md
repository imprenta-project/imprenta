# @imprentajs/xlsx

The spreadsheet writer as a Node addon. See the root `CLAUDE.md` for the rules
that apply everywhere.

## What is generated and what is written

```
index.js               generated by napi — do not edit
index.d.ts             generated by napi — do not edit
imprenta-xlsx.*.node   the compiled crate
src/stream.ts          written by hand: Book, a thin wrapper over WorkbookStream
```

Rebuild after any change under `crates/`:

```bash
pnpm --filter @imprentajs/xlsx build
```

## What gets published

Six packages, not one: `@imprentajs/xlsx` and an `@imprentajs/xlsx-<platform>` for
each entry in `napi.targets`. See `packages/pdf/CLAUDE.md` for the shape — it
is the same, including the rule that **`files` must not list `*.node`**.

## The API, and why it is that shape

- `write(ir)` → `{ xlsx, bytes, sheets }`
- `writeToFile(ir, path)` → no Buffer ever exists; use it for anything large
- `new Book(sheets, { path })` from `@imprentajs/xlsx/stream` — feed rows in

`ir` is a **JSON string**. Faster than walking an object across the boundary,
and it is also what arrives from a file, a queue or an HTTP body.

## Book rules

- **Await every call before the next.** A second one while the first is
  running is refused. A spreadsheet is written in order.
- **The sheets are declared up front, the rows are not.** Names, columns and
  frozen panes go in the constructor, because the package names every sheet in
  its first entry; rows are what a streaming producer does not have yet.
- **Merges can come late.** They are written after the rows, which is what
  lets a total row's span be decided once the row count is known.
- **Batch size is not a speed question here.** Measured: 0.38 s for two
  hundred thousand rows whether the batch is 1 or 100,000, because there is no
  thread to hop — unlike the PDF side, where it dominated. It changes only
  what the caller holds.

## Testing

`test/write.test.ts` covers what needs Node running: promises, rejection,
ordering, the file-versus-buffer paths.

`test/together.test.ts` loads **both addons in one process, in both orders**.
It is a regression test for a bug that aborted the process rather than
throwing, so a failure there looks like a crashed worker and not a failed
expectation. Do not delete it, and do not add a `#[global_allocator]` to the
xlsx crate.

The test that matters most: content fed in pieces is byte for byte what the
same content declared whole produces.
